Enumerating and testing the standard services found in real organizations, internally and externally, and checking each against its known weaknesses and misconfigurations.

**Key concepts to own:** per-service enumeration checklist; misconfiguration vs vulnerability; service-specific attacks.

## The module's frame (read this first)

- **The attack concept (§2):** every attack decomposes into **Source** (what sends the request — input, code, config) → **Process** (what handles it, where the flaw triggers) → **Privileges** (what it runs as) → **Destination** (what it reaches). The module maps each "latest vulnerability" section onto these four boxes — do the same for any new CVE and you understand it faster. Log4j is the worked example: header input (source) → written to a log → the logging library *executes the lookup instead of treating it as text* (process, high privileges) → code runs, sometimes on internal servers users never touch directly.
- **Misconfiguration before vulnerability (§3):** defaults unchanged, anonymous access enabled, access rights broader than the role (an upload-only user who can also delete), unnecessary features/pages/accounts, error pages leaking stack traces. Check these first — they are more common than CVEs. Hardening = change every default, disable admin/debug surfaces, audit configs automatically, segment, add security headers.
- **Clue-chaining (§4):** treat enumeration as detective work — every find is a potential credential or pivot elsewhere (the lesson's chain: anonymous FTP → a filename → email credentials → a password in the mailbox → a database that executes commands). Never dismiss a "useless" clue.

## Deep summary — section by section (original words)

**1. Interacting with Common Services** — Know each service's purpose, client and post-connection power before attacking it. SMB browsable from Windows (Explorer, `net use`) and Linux (`mount -t cifs` with a credentials file); mail = SMTP send + POP3/IMAP read; databases via CLI clients or GUI tools (dbeaver, SSMS, MySQL Workbench) — and the **service account's privileges** decide whether SQL can become OS command execution (possible on MSSQL/PostgreSQL per the lesson, not MySQL). Troubleshooting runs off error codes: authentication → privileges → network → firewall → protocol support. *(3 embedded demo videos not played — text read.)* *Use: both.*

**2. The Concept of Attacks** — See "The module's frame" above. Pitfall: assuming the destination of round one is the source of round two — re-map the four boxes each cycle. Defence habit: treat all input as untrusted; never let a logging library execute lookups in log data. *Use: both.*

**3. Service Misconfigurations** — See frame above. Workflow: banner → identify → defaults → anonymous access → access-model review. *Use: both.*

**4. Finding Sensitive Information** — See frame above. Sensitive = usernames, emails, passwords, DNS records, IPs, source code, configs, PII. Defence: no credential reuse across services; never store credentials in mailboxes or files. *Use: both.*

**5. Attacking FTP** — TCP/21. Enumerate with banner + the `ftp-anon` NSE script; anonymous login (user `anonymous`, no password) is the first test — dangerous when it includes **write**. Then browse/transfer (`get/mget`, `put/mput`); brute force with Medusa where needed (lockouts/captchas blunt it). The **FTP bounce** attack abuses PORT to make the server connect onward — historically a way to scan internal hosts through an external FTP server; modern servers block it. Defence: disable anonymous unless required; strong credentials + lockout. *(3 Q — gap.)* *Use: both.*

**6. Latest FTP Vulnerabilities** — CoreFTP (pre-build 727, CVE-2022-22836): the upload endpoint also honours HTTP PUT, and a traversal path in the PUT writes **outside** the service directory — anywhere the service account can write. Concept-mapped: user-controlled method/path (source) → path misinterpreted (process) → loose authorization (privileges) → chosen file written (destination). Defence: reject unexpected methods on upload endpoints; normalize/resolve paths before writing. *Use: both.*

**7. Attacking SMB** — TCP 445 (legacy 139/NetBIOS). The full menu: enumerate version/shares (`smbclient -N -L`, smbmap, enum4linux-ng) → test **null sessions** (can leak users/shares via rpcclient) → brute/spray with CrackMapExec/NetExec (lockout risk on domain accounts) → command execution as the service account (Impacket psexec/smbexec/atexec) → enumerate logged-on users, dump SAM, **pass-the-hash** → **forced authentication**: Responder/ntlmrelayx trick a server into authenticating to you, yielding a NetNTLM hash (hashcat `-m 5600`) to crack or **relay**. Defence: disable null sessions and SMBv1, require signing, lockouts, monitor SMB auth. *(3 Q — gap.)* *Use: both.*

**8. Latest SMB Vulnerabilities** — **SMBGhost (CVE-2020-0796)**: unauthenticated RCE in SMBv3.1.1 compression — a crafted request triggers an integer overflow in the SMB driver during negotiation, overwriting memory that then executes. Affects specific Windows 10 builds (1903/1909); exploitation can crash the target. No exploitation steps in the lesson — pure concept mapping. Defence: patch; disable compression where unneeded. *Use: both.*

**9. Attacking SQL Databases** — MSSQL (1433, UDP 1434 browser, hidden mode 2433) and MySQL (3306) hold the crown jewels. After login, **privileges decide everything**: enumerate databases/tables, then according to rights — command execution (MSSQL **xp_cmdshell**, disabled by default, enabled via sp_configure, runs as the service account; MySQL via UDFs), file write (SELECT … INTO OUTFILE, gated by secure_file_priv; MSSQL Ole Automation), file read (LOAD_FILE, OPENROWSET(BULK)), **service-hash capture** (xp_dirtree/xp_subdirs pointed at your SMB listener → NetNTLMv2, `-m 5600`), **impersonation** (EXECUTE AS LOGIN), and **linked servers** (run commands on another DB where you're sysadmin there). Don't confuse the SQL user's privileges with the service account's. Defence: least privilege, xp_cmdshell/Ole Automation off, block outbound SMB from DB servers. *(2 Q — gap.)* *Use: both.*

**10. Latest SQL Vulnerabilities** — No CVE needed: **xp_dirtree hash theft**. Point the undocumented procedure at an attacker-controlled share; the MSSQL service authenticates over SMB *as its service account*, handing you its NTLMv2 hash to crack or relay. Easy to overlook precisely because it abuses an intended function. Defence: block outbound SMB from database servers; least-privilege service accounts. *Use: both.*

**11. Attacking RDP** — TCP/3389. Password attacks are the norm, but **spray, don't hammer** — one password across many users stays under lockout thresholds (Crowbar/Hydra). With admin/SYSTEM you can **hijack another user's live session** with `tscon` (broken on Server 2019). Pass-the-hash over RDP needs **Restricted Admin Mode** enabled on the target — a registry value that defaults to off, so treat PtH-RDP as conditional, not standard. Defence: strong passwords + lockout + MFA; don't enable Restricted Admin. *(3 Q — gap.)* *Use: both.*

**12. Latest RDP Vulnerabilities** — **BlueKeep (CVE-2019-0708)**: wormable, unauthenticated RCE in the initial RDP settings exchange — a use-after-free lets freed kernel memory be reused to run attacker code as LocalSystem. ~950k systems were found exposed in 2019 scans. No exploitation steps — concept mapping only. Defence: patch; never expose RDP directly — gateway/VPN. *Use: both.*

**13. Attacking DNS** — UDP/TCP 53. Three plays: **zone transfer** (`dig AXFR @ns domain`) — if allowed, you get the whole namespace; **subdomain enumeration** (passive: Subfinder; brute force: Sublist3r/Subbrute/Fierce) — including hunting **dangling CNAMEs** pointing at dead third-party services, which you can re-register and **take over**; **spoofing/cache poisoning** from a man-in-the-middle position (Bettercap/Ettercap DNS spoofing). A takeover fails if the third-party service is actually still registered. Defence: restrict transfers to authorized servers; audit records continuously; delete orphaned CNAMEs. *(1 Q — gap.)* *Use: both.*

**14. Latest DNS Vulnerabilities** — Subdomain takeover at scale: companies cancel a service but leave the CNAME; anyone can claim the name on that service and serve content (read: phishing) under the company's subdomain. Studies found hundreds of thousands of dangling records; it's a standing HackerOne bounty category. Verify with the provider's own "not found" response, not just a blank page in a browser. Defence: continuous DNS auditing; remove records for dead services. *Use: both.*

**15. Attacking Email Services** — SMTP (25/465/587), IMAP (143/993), POP3 (110/995). Find the server via **MX records**; enumerate users via SMTP **VRFY/EXPN/RCPT TO** and POP3 USER (smtp-user-enum automates) — cloud mail needs cloud-aware tooling (O365spray, MailSniper, CredKing) and changes defences fast. Spray/brute force as elsewhere (Hydra). Test for an **open relay** (Nmap smtp-open-relay, swaks) — an unauthenticated relay is a phishing goldmine. Defence: disable VRFY/EXPN, require auth, close relays, MFA on mail accounts. *(2 Q — gap.)* *Use: both.*

**16. Latest Email Service Vulnerabilities** — **OpenSMTPD ≤ 6.6.2 (CVE-2020-7247)**: unauthenticated RCE — a semicolon crafted into the sender field breaks out of the SMTP parser into shell command execution, constrained by a 64-character buffer. Runs on Debian/Fedora/FreeBSD; thousands of servers were publicly reachable. Defence: patch; validate sender fields; don't run mail services as root. The section also names follow-on practice machines (OWA brute force, phishing/inbox enumeration themes). *Use: both.*

**17–19. Skills Assessments — Easy / Medium / Hard (scenarios)** — Three commissioned servers in the fictional inlanefreight.htb domain, each with a flag file to reach: **Easy** = the externally visible mail/customer-files server (enumerate → attack the exposed service); **Medium** = an internal, rarely used mail/files/backup server (the work is *reaching* an internal host, not just attacking an exposed one); **Hard** = an internal files + database server with a chained path (retrieve a user's file → find a user's password → use it to reach the next user → flag on the Administrator Desktop). Morals: internal and rarely used servers get hardened too, and chains beat single-service thinking. *(1 + 1 + 4 Q — gap; scenario text only.)* *Use: engagement.*
