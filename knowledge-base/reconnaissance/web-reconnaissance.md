# Web Reconnaissance

## Purpose

Web reconnaissance converts scattered public and target-derived observations into a validated attack-surface inventory. Its outputs feed vulnerability assessment; they are not vulnerabilities by themselves.

## Recon Layers

| Layer | Questions |
|---|---|
| Registration | Who registered the domain, when, and through which registrar? |
| DNS | Which names, addresses, mail systems, and authoritative servers exist? |
| Certificates | Which hostnames have appeared in TLS certificates? |
| HTTP routing | Which sites and virtual hosts respond on each address? |
| Technology | Which servers, frameworks, CMSs, WAFs, and libraries are indicated? |
| Content | Which routes, scripts, forms, files, APIs, and metadata are exposed? |
| History | What existed previously and may still be reachable? |
| People/process | Which public documents, repositories, and naming patterns explain the environment? |

## Identity Sets Must Stay Separate

```text
Registered domains ≠ DNS names ≠ resolved hosts ≠ live web services ≠ virtual hosts
```

Track relationships explicitly. One IP can host many vhosts; a CT hostname may no longer resolve; a DNS name may expose a non-web service.

## DNS Intelligence

DNS records reveal infrastructure relationships, mail flow, third-party providers, service discovery, and security controls. Query specific types and authoritative servers when appropriate. Normalize trailing dots, case, wildcards, aliases, and duplicate results.

Before brute forcing:

1. test random labels for wildcard DNS;
2. choose a wordlist based on target language and naming patterns;
3. use controlled concurrency;
4. resolve through approved resolvers;
5. validate results with record type, IP, TTL, and HTTP behavior.

AXFR testing is a configuration check against each authoritative name server. A successful transfer may expose far more than public navigation and should be treated as sensitive evidence.

## CT and Historical Data

Certificate Transparency provides a historical set of certificate names, not a current asset list. Normalize SAN entries, remove wildcards, resolve each candidate, and record first/last-seen context where available.

Web archives and search indexes can expose retired endpoints, parameters, documents, JavaScript, technologies, and naming conventions. Historical data becomes actionable only after current ownership and reachability are validated.

## Vhost Discovery

Name-based hosting routes requests using the HTTP `Host` header. Vhost discovery therefore compares responses generated by candidate hostnames against a random-host baseline.

Useful comparison fields:

- status code;
- byte length;
- word/line count;
- page title;
- redirect target;
- body hash;
- TLS certificate behavior.

Avoid accepting every response when the server returns a default page for unknown hosts.

## Fingerprinting as Evidence Fusion

No single header or scanner proves a technology and version. Confidence improves when independent indicators agree:

```text
Header + cookie + HTML path + script signature + error behavior + TLS/WAF signal
```

Redirect chains can expose canonical domains and separate infrastructure layers. WAF detection affects scan safety and interpretation, not authorization to evade controls.

## Crawling, Fuzzing, and Metadata

- Crawling follows discovered links and maps reachable structure.
- Fuzzing tests candidate names and paths.
- Both can create load and must respect scope and rate limits.

Inspect `robots.txt`, sitemaps, security.txt, OpenID/OAuth discovery, JWKS locations, HTML comments, JavaScript, source maps, manifests, forms, documents, backups, and metadata.

`robots.txt` is advisory. It neither protects content nor grants permission.

## Search and Archive Correlation

Search operators efficiently locate indexed pages and files. Results may be cached, stale, mirrored, third-party, or out of scope. Preserve the query and result source, then validate the actual owner and current endpoint separately.

## Automation Principles

Automation should be:

- reproducible: exact command, version, configuration, and wordlist;
- scoped: approved targets and rate limits only;
- modular: separate passive, DNS, HTTP, crawl, and content phases;
- observable: raw results and errors retained;
- validated: important findings manually confirmed;
- deduplicated: canonical hostnames and URLs maintained.

## Evidence Model

For each asset, record:

| Field | Example |
|---|---|
| Asset | `portal.example.com` |
| Source | CT, DNS brute force, crawl, archive |
| Resolution | IPs and aliases |
| Protocol | HTTP/HTTPS and port |
| Evidence time | timestamp |
| Technology | indicators and confidence |
| Scope status | in / out / pending confirmation |
| Notes | auth, redirects, WAF, interesting paths |

## Common Failure Modes

- treating scanner output as fact;
- confusing a wildcard response with a valid host;
- testing third-party infrastructure without scope confirmation;
- skipping alternate ports, redirect destinations, or vhosts;
- relying on one wordlist or one passive source;
- ignoring historical data;
- failing to save raw output;
- automating before understanding manual checks;
- collecting excessive sensitive data.
