Keeping notes and writing the final report so findings are reproducible, impacts are clear to non-technical readers, and your documentation holds up if anything goes wrong mid-test.

**Key concepts to own:** note discipline during testing; finding structure; evidence quality; audience-aware writing.

**The module in one line:** a test you cannot reconstruct from your notes never happened — document as you go, and the report writes itself.

## Deep summary (original words)

**1. Introduction** — A pentest is a snapshot in time; the report is its durable record and must pin down the boundaries (engagement type, testers, source IPs, special considerations, testing window, disclaimer). The failure modes are all documentation failures: notes that don't exist, scope/exclusions nobody wrote down, scans whose impact can't be explained afterwards. Build reporting into the engagement from day one; sync notes daily. *Use: both.*

**2. Notetaking & Organization** — A fixed note structure (attack path, credentials, findings, research, AD/OSINT, admin/scoping, activity + payload logs) inside a fixed folder tree (Admin, Deliverables, Evidence, Findings, Scans, Notes, OSINT, Wireless, Logging, Misc, Retest) lets *anyone* — including a teammate taking over mid-test — reconstruct the engagement. Log everything with **Tmux logging** (plugin + TPM, retroactive capture, high history limit); track exploitation attempts, artifacts left behind, and every account/system change (written approval first). One note per finding, evidence attached. Hygiene rules that matter: **redact with solid bars, never blur/pixelate** (reversible), prefer terminal output over screenshots, paste output as plain text, `<SNIP>` gaps, trim the middle of hashes, and don't hoard client PII you don't need (GDPR). Tooling: Obsidian locally, Outline in the cloud, both Markdown-friendly. *(3 Q — gap.)* *Use: both.*

**3. Types of Reports** — The report must match what was commissioned: a **vulnerability assessment** is scan-led with no exploitation and false-positive validation — never dress it up as a pentest. Pentest flavours (black/grey/white box; zero/hybrid/evasive; internal/external) and adjacent disciplines (Purple Team, Cloud, IoT, Web App, Hardware) each shape the document. Deliverable family: Draft → Final → Post-Remediation → Attestation, plus decks, a findings spreadsheet, and **immediate vulnerability notifications** for the can't-wait findings (internet-exposed unauthenticated RCE, sensitive-data exposure, default creds). *(2 Q — gap.)* *Use: engagement.*

**4. Components of a Report** — Anatomy: executive summary, **attack chain narrative** (the story of the compromise, link by link), findings prioritized by impact (consolidate the informationals), short/medium/long-term recommendations, appendices. Exec summary discipline: non-technical, plain language, ~1.5–2 pages, no vendor pitches. Appendices split into static (scope, methodology, severity ratings, bios) and dynamic (exploitation attempts/payloads, compromised credentials, configuration changes, additional affected scope, information gathering, domain password analysis — DPAT). Report shape flexes by engagement type (web app, physical, red team). *(2 Q — gap.)* *Use: engagement.*

**5. How to Write Up a Finding** — The core skill. Minimum fields: description/platforms, impact, affected systems, recommendation, references, **steps to reproduce with evidence** — one figure per step, configuration shown in full, narrative between figures, alternative tools named. Optional: CVE, OWASP/MITRE IDs, CVSS, ease/probability. A finding is defensible when the client can reproduce it on their own host; a remediation is good when it's **exact and testable** (precise settings/paths, test-first warnings, an interim workaround if the real fix is heavy) — "reconfigure the registry" is not a remediation. References: vendor-agnostic, thorough, freely accessible — write your own if none exists. Screenshots stay professional (no stray bookmarks/extensions). WriteHat is the lesson's findings-database/report tool. *(2 Q — gap.)* *Use: engagement (and CTF write-ups).*

**6. Reporting Tips and Tricks** — Write the report **during** the test: blank template per assessment type (never copy a previous client's report — their name/data can leak into yours), styles/captions/numbering set up front, macros for recurring data, a sanitized template findings library, client notified at start and end of each testing day. QA is a process, not a glance: at least one full round by a non-author, ideally split technical-accuracy vs styling, and the reviewer never silently rewrites findings. Deliver Draft → review meeting (~a week later) → FINAL, then archive all data per retention policy (at least until retest). Platform options span free (Ghostwriter, Dradis, VECTR, WriteHat) to paid (AttackForge, PlexTrac, Prism). Sanitize unprofessional tool output case-by-case; never send client data to online grammar tools. *(Theory.)* *Use: engagement.*

**7. Practice Lab (scenario)** — Take over an internal pentest mid-flight from a departed tester: their notes + evidence cover only some of 13 findings; you set up Tmux logging, re-derive the missing evidence, complete the test, and draft the report (WriteHat or the provided template). It is the handover problem from §2 made concrete — and, with Module 28's report, the module's stated best prep for report-graded HTB exams. Save practice data locally; lab resets wipe the VM. *(5 Q — gap; scenario text only.)* *Use: engagement.*

**8. Beyond this Module** — Writing is a career skill built by volume: treat boxes/labs as real engagements and write findings from templates (even 1–2 per box compounds into a personal findings database), read public pentest reports for style, blog, seek feedback, develop *your own* style rather than copying one. Named next steps: Penetration Testing Process (Module 1) for the full picture, then the capstone — Attacking Enterprise Networks. *(Theory.)* *Use: both.*
